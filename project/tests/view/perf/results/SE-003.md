**프록시 기준**: 캐릭터는 708 tri 정적 프록시이며 스킨·애니메이션·툰 셰이더가 없다.

### 유효성 요약 (qa 확인)

4개 모두 17개 필수 키 존재, `run_valid=true`, `run_issues=[]`, `headless=false`, `vsync=off`, `renderer=forward_plus`(metal), 실제 GPU, 해상도 1920×1080 일치, 예열 ≥ 10 s·≥ 120 프레임(C 는 18.5 s/120, D 10.19 s/120), 측정 ≥ 30 s, `sample_count` = `avg_fps × 30` 의 ±0.3% 이내, 인스턴스·라이트·셰도우 수가 티켓 표와 일치(실측 `*_actual` 도 일치), 메시 708 tri ≤ 800, 아틀라스 2048.
통계: `avg_fps × avg_frame_ms` = 1000 (오차 1e-12), `1000/p1_low_frame_ms` = `p1_low_fps`, `sample_count × avg_frame_ms` = `measure_sec`, `avg ≤ p1_low ≤ max ms` 전부 성립.

### 런타임 가시성 증거 (컬링 없음)

| 구성 | primitives / (인스턴스 × 708) | A 대비 primitives 비 |
|---|---|---|
| A | 1.0001 (3,540,238 = 5,000 × 708 + 238) | 1 |
| B | 25.0001 | 25.00 |
| C | 97.0004 | 96.99 |
| D | 25.0001 (= 10,000 × 708 × 25) | 50.00 |

A 는 5,000 × 708 = 3,540,000 에 UI·바닥 238 만 더해져 군중이 하나도 컬링되지 않는다. 비는 정수에 0.01% 이내로 맞는다: B = 1 + 24, C = 1 + 96, D = 2 × B. 즉 셰도우를 켠 라이트가 군중 **전체**를 다시 그리고 있다(가설 확인). 24 와 96 은 "라이트 한 쌍(Omni 1 + Spot 1)당 6패스"(예: Omni 큐브 5면 + Spot 1면, 위쪽 면은 군중이 라이트 아래라 제외로 추정)이거나 "Omni 당 6패스, Spot 0" 으로 읽을 수 있고 이 데이터만으로는 구분되지 않는다. 어느 쪽이든 C/B = 정확히 4.00 이므로 C 에서 아틀라스 슬롯 부족으로 그림자가 생략된 흔적은 없다(C 는 "낮게 나온 값" 아님).

### 바운드 분석 (AC8)

`avg_gpu_ms` 는 네 구성 모두 0.0 이다. 측정기는 `viewport_set_measure_render_time(true)` 후 `viewport_get_measured_render_time_gpu()` 를 읽는데, 이 환경(Godot 4.7.2 / Metal)에서 GPU 타임스탬프 값이 오지 않은 것으로 보인다(원인 확정은 못 함: Metal 타이밍 미지원 또는 측정기 설정 문제 가능). 그래서 `bound_hint` 는 "unknown" 이고 GPU 시간은 직접 측정하지 못했다. 대신 구성 간 차분으로 추정한다.

| 비교 | 평균 ms 차 | 추가 패스(primitives 기준) | 패스당 ms | 추가 Mtri 당 ms |
|---|---|---|---|---|
| B − A (셰도우 라이트 8개) | +35.44 | 24 | 1.48 (셰도우 라이트당 4.43) | 0.417 |
| C − A (셰도우 라이트 32개) | +145.00 | 96 | 1.51 (라이트당 4.53) | 0.427 |
| D − A (인스턴스 2배, 라이트 8개) | +74.35 | 48 (군중 5,000 환산) | 1.55 | 0.429 |

- 프레임 시간 증가가 추가 primitives 에 거의 선형이다(0.42~0.43 ms/Mtri, 편차 3% 이내). 비용이 셰도우 패스의 삼각형 처리량에 비례한다는 강한 정황이다. C − B = 109.56 ms / 24 패스 = 4.56 ms/라이트.
- CPU 측 `avg_crowd_update_ms` (GDScript 군중 보간·버퍼 갱신 + 라이트 갱신)의 프레임 대비 비율: A 2.88 ms = 27.1%, B 6.04 ms = 13.1%, C 9.70 ms = 6.2%, D 9.22 ms = 10.9%. `avg_render_cpu_ms`: A 0.16, B 0.49, C 1.39, D 0.29 ms (각 프레임의 1.1% 이하). B 에서 두 CPU 항목 합 6.53 ms 는 프레임의 14.2% 이고 나머지 39.5 ms (85.8%) 는 이 두 항목 밖이다. 같은 GDScript 작업인데 군중 갱신 ms 가 A 2.88 → B 6.04 → C 9.70 으로 셰도우 수에 따라 늘었다. 순수 CPU 연산이 아니라 GPU 가 바쁠 때 MultiMesh 버퍼 업로드가 대기한 시간이 섞였을 가능성이 있다(추정, 미확인). 어느 쪽이든 CPU 항목이 프레임의 대부분을 설명하지 못한다.
- 결론(추정, 직접 측정 아님): B 의 지연은 CPU 스크립트가 아니라 셰도우 패스(군중 전체를 라이트 면마다 다시 그리는 GPU 작업, 혹은 Metal 쪽 인코딩·제출)에서 온다. A→B→C→D 차분이 primitives 비와 선형으로 맞는 것이 근거다. GPU 시간 직접 측정(Xcode Metal GPU 캡처/카운터, 또는 `avg_gpu_ms` 가 나오는 환경)은 후속에서 한다.
- 인스턴스 확장(D vs B): 군중 갱신 ms 는 6.04 → 9.22 (×1.53, 인스턴스 ×2 보다 낮음, 고정비 포함), 프레임 시간은 46.06 → 84.96 (×1.84).
- 참고 이상치: A 의 `avg_process_ms`(Performance.TIME_PROCESS) 는 13.93 ms 로 평균 프레임 10.61 ms 보다 31% 크다(B/C/D 는 0.7% 이내로 일치). A 의 1% low 50.9 fps, 최대 30 ms 도 B~D 에 비해 편차가 큰 편이다. 원인 미확인. 이 값은 판정(B)에 쓰지 않으며, A 를 13.93 ms 로 보더라도 B − A = 32.4 ms 로 결론은 같다.

### 최소 사양 맥락

측정 기기는 Mac mini M1 의 **내장(통합) GPU** 다. 데스크톱 dGPU 가 아니므로 PRD 성능 목표의 60fps 기준 기기(게이밍 PC)가 아니고, 최소 사양(내장 그래픽 Intel Iris Xe, 30fps) 쪽에 가까운 부류다. 두 GPU 의 상대 성능은 qa 가 측정하지 않았으므로 단정하지 않는다. 따라서 이 결과만으로 "Godot forward_plus 가 PRD 60fps 목표를 못 맞춘다"고 결론낼 수 없고, **Unity 재검토(ADR-0001)는 qa 가 판단하지 않는다**(사람·producer 결정). 판단에 필요한 측정은 둘이다: (1) 셰도우 최적화(후속 SE-013) 후 같은 M1 에서 재측정, (2) 게이밍 PC(dGPU) 에서 같은 절차로 A~D 재측정. 최소 사양(Intel Iris Xe 30fps) 자체는 검증 불가(해당 하드웨어 없음). 참고로 이 M1 의 B 는 30fps 에도 못 미친다(21.7 fps).

최소 사양(Intel Iris Xe 30fps): 검증 불가(해당 하드웨어 없음). 하드웨어가 생기면 같은 명령으로 측정하고 이 줄을 바꾼다.

### 에이전트 환경 참고 수치 (무효, 판정에 쓰지 않음)

render-engineer 가 llvmpipe(gl_compatibility)에서 얻은 primitives 비(B/A 25, C/A 97)는 M1 forward_plus 실측 비(24.998, 96.994)와 일치한다. 즉 셰도우 패스 구조는 렌더러와 무관하게 같다.

## 측정 방법

저장소 루트에서, Godot 에디터를 닫고, 전원 연결(노트북), 다른 무거운 프로그램 없이:

```bash
mkdir -p docs/reports/perf
for c in A B C D; do
  godot --path project res://view/perf/spike_crowd.tscn -- --measure --config=$c --out="$PWD/docs/reports/perf/SE-003-$c.json"
done
```

Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force docs/reports/perf | Out-Null
foreach ($c in "A","B","C","D") {
  godot --path project res://view/perf/spike_crowd.tscn -- --measure --config=$c --out="$PWD/docs/reports/perf/SE-003-$c.json"
}
```

- `--out` 이 없으면 `user://perf/SE-003_<config>.json` (Linux `~/.local/share/godot/app_userdata/Stage Empire/perf/`,
  Windows `%APPDATA%\Godot\app_userdata\Stage Empire\perf\`).
- 각 실행은 약 40초(예열 10초 + 측정 30초) 뒤 스스로 종료하고, 콘솔에 위 표 형식의 한 행과 관문 판정을 찍는다.
- 측정 스크립트가 런타임에 VSync off, 프레임 제한 해제, 테두리 없는 1920×1080 창을 설정한다(`project.godot` 은 바꾸지 않는다).
- JSON 의 `run_valid` 가 false 면(`run_issues`: 헤드리스, VSync 켜짐, forward_plus 아님, 해상도 불일치) 그 측정은 표에 넣지 않고 다시 잰다.
  관문 구성에서 조건 위반이면 `gate.verdict` 가 "무효"다.
