## 관문 실패와 병합 (producer 판단용 의견)

- **병합 차단 사유 아님.** 티켓 산출물(씬, 설정, 측정기, 테스트, 결과 표 4행, 판정 한 줄, 바운드 분석)은 전부 있고 AC1~AC10 중 AC8 은 "판정이 기록돼 있다"는 기준이지 "통과"가 기준이 아니다. 이 브랜치를 병합해야 SE-013 이 같은 씬·측정기로 재측정할 수 있다.
- **ADR-0001 "실패 시 Unity 재검토"를 셰도우 최적화 후 재측정 뒤로 미루는 것은 타당하되 기한과 기준 기기가 필요하다.** 미룰 근거: (a) 측정 기기 Mac mini M1 통합 GPU 는 PRD:176 의 60fps 기준 기기가 아니라 최소 사양(Iris Xe 30fps) 부류다. (b) 구성 A(셰도우 0)가 94.2 fps 로 인스턴싱·라이트 32개 자체는 M1 에서도 여유가 있고, 실패 요인은 "셰도우 라이트가 군중 전체를 24번 다시 그림"(B/A primitives 25.0)이라는 단일 병목이며, 이는 PRD 가 이미 계획한 32×32 청크 구조·저폴리 셰도우 메시로 줄일 수 있는 엔지니어링 문제다. 즉 지금 결과는 "출시 구성이 아닌 최악 구성"의 수치다. 미루면 안 되는 이유의 반대편: ADR-0001 과 PRD:326 은 결정 시점을 "프리프로덕션 4주 안"으로 묶었고, M1 의 B 21.7 fps 는 최소 사양 목표 30fps 에도 못 미친다. 따라서 producer 는 (1) `docs/adr/0001-engine-godot-4.md` 상태 줄에 "1차 측정 실패(M1, 2026-10-09, B 21.7 fps) — SE-013 재측정 후 결정, 기한 <날짜>" 를 덧붙이고(ADR 대체가 아닌 상태 갱신, producer 쓰기 범위 `docs/adr`), (2) SE-013 수용 기준에 60fps 기준 기기(dGPU 게이밍 PC)와 30fps 기준 기기(M1 또는 Iris Xe)를 명시해야 한다. 재측정에서도 B < 60(기준 기기)이면 그때 Unity 재검토 ADR 이다.
- 1% low 정의(가장 느린 ceil(1%) 프레임의 평균 ms 의 fps, `perf_stats.gd:8-9,48-54`)는 업계 통례이고 qa 가 통과로 봤다. 티켓 문구 "평균 fps" 는 두 가지로 읽히므로 producer 가 `docs/tickets/SE-003.md:38` 을 구현 정의로 고정해 두면 된다(참고).

## 참고 (규칙 근거 없음, 메모)

- `spike_crowd.gd:129-133` 의 CPU 계측(`last_advance_usec`)은 제품 view 코드 안의 측정 도구다. 발견 사항 1 을 고칠 때 측정기가 `advance()` 를 직접 감싸면 view 에서 `Time.*` 가 사라진다.
- 측정 JSON 의 `commit` 이 `-dirty`(B·C·D)인 것은 qa 가 원인(미추적 측정 JSON)을 확인했다. `resolve_commit()`(`measure_spike.gd:294-307`)이 `git status --porcelain` 전체를 보는 대신 `project/ tools/` 만 보게 하면 사라진다. SE-013 에서 같이.
- qa 가 지적한 A 의 `avg_process_ms`(13.93 ms) > 평균 프레임(10.61 ms) 이상치는 판정과 무관. `Performance.TIME_PROCESS` 는 이전 프레임 값이라 fps 가 높은 A 에서 프레임 간 편차가 섞인 것으로 보이지만 확인하지 않았다.
- `docs/tickets/SE-003.md:5` 상태는 "측정 완료 — 관문 실패, SE-013 후속". 병합 시 producer 가 "완료(관문 실패)" 등으로 갱신. `docs/status/2026-W41.md:92` 가 다음 번호를 SE-013 으로 예약해 뒀고 티켓 파일은 아직 없다.
