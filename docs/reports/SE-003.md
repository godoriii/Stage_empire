### AC2 대조군 평가

구현자 대조군은 "군중 중심에서 카메라 오른쪽 방향으로 가로 반폭의 98% 지점은 안, 102% 지점은 밖" 하나다. 이는 `is_position_in_frustum` 이 가로 방향으로 작동한다는 것만 증명한다. 한계 3가지:
1. `_count_outside_frustum`(실제 5,000개를 세는 함수)이 0 이 아닌 값을 낼 수 있는지는 한 번도 보이지 않는다. 항상 0 을 돌려주는 버그가 있어도 통과한다.
2. 세로 가장자리(상·하)는 대조군이 없다. 실제 여유가 가장 작은 쪽이 세로다(상 55.9 px).
3. 군중이 화면에 비해 아주 작아도 통과한다.

qa 보강(`test_spike_qa.gd`)으로 세 가지를 모두 채웠다. 결과: 최대 줌아웃에서 모든 인스턴스가 1920×1080 화면 안, 가장 가까운 변까지 55.9 px, 가로 89.4% 점유. 즉 AC2 는 통과이고 여유도 충분하다. 단, 이 검사는 인스턴스 "위치(발·머리 꼭대기 점)"가 대상이라 캐릭터 폭(±0.3 m ≈ 10 px) 은 위 여유 안이다. GPU PC 측정에서는 `primitives` 로 런타임 증거를 한 번 더 얻는다(아래 "측정 후 절차" 3단계).

## 리뷰어에게

구현자가 "티켓과 다르게 한 것" 판단 (AC 위반 여부):

1. 군중 영역 약 50.5 m (티켓 100×100 m): **타당한 해석, AC 위반 아님.** qa 가 값을 재계산했다. SE-002 최대 줌아웃 size 32(`zoom_sizes = 7,12,20,32`, 피치 −30°)에서 세로 32 m, 16:9 가로 56.9 m. 지면 깊이 `(32 − 1.81·cos30°)/sin30° = 60.9 m`, 폭과 깊이의 작은 쪽 56.9 × fill 0.9 − 2×0.35 = 50.5 m. 100×100 m 를 요 45° 로 놓으면 대각이 141 m 라 한 화면에 들어갈 수 없고, 범위 문구("100×100m")와 AC2("전부 화면 안, 컬링으로 숫자를 깎지 않는다")가 충돌한다. AC 는 검증 가능한 기준이므로 AC2 를 따른 것이 맞다. 영향: 밀도가 약 2명/m²(100×100 이면 0.5명/m²)로 더 높아 오버드로·셰도우 비용 면에서 보수적(어려운) 쪽이다. 통과/실패 숫자를 낙관 방향으로 왜곡하지 않는다. producer 는 이 편차를 `results/SE-003.md` 에도 한 줄 적게 해야 한다(현재 표에는 없음).

## 측정 후 절차 (수행 완료: 위 "측정 결과"가 이 절차의 실행 기록)

### 파일 위치와 인계

- 사람 실행 명령은 티켓 "결과" 절 및 `project/tests/view/perf/results/SE-003.md` 의 "측정 방법"(구성 A~D 각 1회, 약 40 초). 권장 추가 인자: `--commit=$(git rev-parse --short=12 HEAD)` (JSON 의 `-dirty` 방지).
- 결과 JSON: `docs/reports/perf/SE-003-A.json`, `SE-003-B.json`, `SE-003-C.json`, `SE-003-D.json` (`--out="$PWD/docs/reports/perf/SE-003-$c.json"`). qa 는 이 4개를 읽는다. 하나라도 없으면 그 구성은 "검증 불가"로 두고 결론은 조건부 유지.
- 사람에게 같이 요청: 측정 PC 사양(GPU 모델, 드라이버 버전, RAM, OS)이 JSON 에 충분히 안 찍히면(`gpu` 빈 문자열 등) 직접 알려 줄 것, 그리고 구성 B 실행 중 화면을 한 장 캡처(육안으로 5,000 캐릭터와 라이트가 보이는지).

### 판정 절차

1. **유효성 검사** (구성마다, 하나라도 어기면 그 JSON 은 표에 넣지 않고 재측정 요청):
   - 17개 필수 키 존재, `run_valid == true`, `run_issues` 비어 있음, `headless == false`, `vsync == "off"`, `renderer == "forward_plus"`, `resolution == requested_resolution == "1920x1080"`.
   - `gpu` 가 실제 GPU 이름일 것. `llvmpipe`, `SwiftShader`, `lavapipe`, `Microsoft Basic Render`, 빈 문자열이면 `run_valid` 와 무관하게 무효(소프트웨어 렌더).
   - 측정 길이를 줄이지 않았을 것: `warmup_sec ≥ 10`, `warmup_frames ≥ 120`, `measure_sec ≥ 30`, `sample_count ≈ avg_fps × 30`(±5%).
   - `instances/lights/shadow_lights` 가 티켓 표와 같고(A 5000/32/0, B 5000/32/8, C 5000/32/32, D 10000/32/8), `instance_count_actual`, `shadow_lights_actual` 이 같을 것, `instance_mesh_tris ≤ 800`, `shadow_atlas_size ≤ 2048`.
   - 네 파일의 `commit` 이 같고 `7e65e11…` 로 시작할 것. `-dirty` 는 더러운 원인이 `docs/reports/perf/*.json` 같은 측정 출력뿐일 때만 허용(사람에게 확인), 코드 변경이 있었다면 재측정. `godot_version` 이 4.7.2 일 것.
2. **통계 재계산**: `avg_fps ≈ 1000/avg_frame_ms`(±0.01), `p1_low_fps ≈ 1000/p1_low_frame_ms`(±0.01), `avg_frame_ms × sample_count ≈ measure_sec × 1000`(±1%), `avg_frame_ms ≤ p1_low_frame_ms ≤ max_frame_ms`. 어긋나면 측정기 버그로 보고 버그 티켓(SE-013-bug 부터).
3. **런타임 가시성 증거(AC2 보강)**: A 의 `primitives ≈ 5000 × 708 = 3,540,000` 에 UI·바닥을 더한 값(구현자 llvmpipe A 에서 3,540,236)인지 확인. 5% 넘게 모자라면 군중 일부가 컬링되고 있다는 뜻이라 "숫자를 깎은" 측정이므로 무효. D 는 약 2 배. `draw_calls > 0`.
4. **표 채우기**: `project/tests/view/perf/results/SE-003.md` 의 PC 사양 10항목과 구성 4행(평균 fps, 1% low fps, 평균 ms, 최대 ms, draw calls, primitives)을 JSON 값 그대로 옮긴다(JSON 의 `format_table_row` 와 같은 소수 자리: fps 1 자리, ms 2 자리). 쓰기는 qa 범위(`project/tests/`)다. 군중 영역 50.5 m 편차와 1% low 정의 한 줄도 같이 적는다.
5. **관문 판정 한 줄** (AC8): 구성 B `avg_fps ≥ 60.0` 이면 "통과", 아니면 "실패". JSON `gate.verdict` 와 qa 계산이 일치해야 한다. 숫자 외의 수식어를 붙이지 않는다. 1% low·최대 ms 는 참고이고 판정에 쓰지 않는다(티켓: 평균 fps). D 는 판정 대상 아님(여유 확인용으로 수치만).
6. **바운드 분석 단락** (B 가 실패일 때 필수, 통과여도 짧게 남기면 좋음): B 의 `avg_frame_ms`(f), `avg_gpu_ms`(g), `avg_crowd_update_ms`(c), `avg_render_cpu_ms`(r), `bound_hint` 로 해석한다.
   - `bound_hint = "gpu"`(g > c + r)이고 g 가 f 의 85% 이상 → GPU 바운드. `"cpu"` 이고 c + r 이 f 의 85% 이상 → CPU 바운드(그중 c 가 크면 GDScript 군중 갱신, r 이 크면 드로우·셰도우 패스 준비).
   - 둘 다 f 의 85% 미만(f > max(g, c + r) ÷ 0.85) → "원인 미분류"로 적고(대기, 드라이버, 프레임 페이싱 등) 추측으로 채우지 않는다. `bound_hint = "unknown"`(g = 0, GPU 시간을 못 재는 드라이버)이면 차분으로 대신한다: 셰도우 비용 = B − A 의 평균 ms, 셰도우 확장 = C − B, 인스턴스 확장 = D − B(c 가 D 에서 약 2 배가 되는지).
   - primitives 비율 `B/A − 1`(예상 약 28 패스), `C/A − 1`(예상 약 112)을 같이 적는다. 크게 모자라면 셰도우 아틀라스 슬롯 부족으로 그림자가 생략된 것이므로 C 값을 "하한이 아닌 낮게 나온 값"으로 표기하고 reviewer 에게 알린다(위 5번 항목).
   - 구현자가 남긴 후속 후보(군중 32×32 청크 분할, `shadow_mesh`, Omni dual paraboloid, 군중 그림자 제외)는 qa 가 채택하지 않는다. 실패 시 producer 에게 숫자와 함께 넘기고, Unity 재검토와 ADR 은 사람과 producer 의 결정이다.
7. **리포트 갱신**: 위 1~3 이 모두 통과한 뒤에만 이 리포트의 AC6(GPU 부분), AC7, AC8 을 갱신하고 결론을 "통과"(B ≥ 60 이고 나머지 AC 통과) 또는 "실패"(B < 60)로 바꾼다. 유효하지 않은 측정이 하나라도 남으면 결론은 조건부로 둔다. 어느 쪽이든 qa 는 ADR 방향을 제안하지 않는다.
8. 최소 사양(Intel Iris Xe 30fps)은 범위 밖이며 "검증 불가(해당 하드웨어 없음)" 그대로 둔다.
