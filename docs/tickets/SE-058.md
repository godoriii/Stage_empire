## 요약

새 게임 직후(설치 0, 첫 저녁 진입 전)에 저장한 파일을 불러오면 `AudienceSystem.coverage.capacity` 가 `0` → `119` 로 바뀐다. 상태 해시가 저장 시점과 달라져 SE-036 AC6("재발행 뒤 해시 == 저장 시점 해시")이 깨진다. 저녁에 진입하면 `BuildSystem` 이 `build.coverage_changed {cause:"sync"}` 를 내서 같은 값으로 수렴하므로 진행 결과는 같지만, 그 사이(낮 구간)의 상태가 다르다.

## 재현 절차

시드 58, 데이터 기본값. 리포지토리 밖 스크립트로 확인했다(`godot --headless --path project -s <probe.gd>`, 제품 코드 변경 없음). 아래 코드가 전부다.

```gdscript
var cfgs: Dictionary = GameSession.load_configs()
var a: GameSession = GameSession.new()
a.new_game_from_configs(58, cfgs)                       # 설치 0, day 1, tick 0
a.saves_dir = "user://probe"; a.autosave_enabled = false
a.bus.publish("session.save_requested", {"slot": "p"})
a.advance(0)                                            # 틱 경계에서 저장
var before: Dictionary = a.snapshot()
var b: GameSession = GameSession.new()
b.new_game_from_configs(777, cfgs)                      # 다른 시드의 새 세션
b.saves_dir = "user://probe"
b.load_from("user://probe/p.sav")                       # true
var after: Dictionary = b.snapshot()
# JSON.stringify(before, "", true) != JSON.stringify(after, "", true)
```

같은 세션에 `session.load_requested {slot: "p"}` 를 보내도 같다.

| 저장 시점 | 로드 직후 해시 == 저장 해시 | 다른 점 |
|---|---|---|
| A. 새 게임 직후(설치 0, 첫 저녁 전) | **아니오** | `/systems/audience/coverage/capacity`: 저장 `0`, 로드 후 `119` (이 한 키뿐) |
| B. 기준 배치 설치 후, 첫 저녁 전 | 예 | 없음 |
| C. 설치 + 섭외 + 첫 저녁 진행 중 | 예 | 없음 |

이어서 진행하면(저장 세션 a 는 그대로, b 는 로드): 로드 직후 불일치, 5틱 뒤 불일치(낮 구간), **1일 진행 뒤(저녁 sync 이후) 일치**.

## 기대 / 실제

- 기대(SE-036 AC6): 불러오기 뒤 재발행이 끝난 시점의 상태 해시 == 저장 시점 해시. 새 게임 직후 저장도 예외가 아니다.
- 실제: 위 표 A 행. 같은 이유로 SE-056 의 `new_game_requested` 는 "재발행 뒤 같은 스냅샷을 한 번 더 `restore`" 하는 우회(`GameSession._new_world`)를 쓰고 있다.

## 원인

- `AudienceSystem._init` 은 `coverage = _empty_coverage()`(`capacity: 0`, `has_stage: false` …)로 시작한다. 첫 `build.coverage_changed` 를 받기 전에는 이 값이다. `BuildSystem.coverage()` 는 빈 맵에서도 `capacity: 119`(바닥 면적에서 나오는 값)를 돌려준다. 즉 새 세계에서 두 시스템의 coverage 가 서로 다른 값으로 시작한다.
- `BuildSystem` 은 설치·철거(`placed`/`demolished`)와 저녁 진입(`sync`)에서만 `build.coverage_changed` 를 낸다. 새 게임 직후부터 첫 저녁(또는 첫 설치)까지는 발행이 없어 `AudienceSystem.coverage` 가 빈 값으로 남는다.
- 불러오기는 `GameSession._publish_loaded` 가 `build.coverage_changed {cause:"sync"}` 를 항상 재발행한다(SE-036 AC6). 이때 `AudienceSystem` 이 처음 `capacity 119` 를 받아 스냅샷과 달라진다. 설치가 하나라도 있었거나 저녁을 한 번 거친 저장은 저장 시점에 이미 같은 값이라 일치한다(표 B·C).
- 영향 범위: 새 게임 직후 ~ 첫 설치/첫 저녁 전 사이의 수동 저장뿐. 오토세이브는 close 에서만 쓰이므로(저녁을 지난 뒤) 해당 없음.

## 영향

- 진행 결과: 저녁 진입 `sync` 가 같은 값을 다시 넣으므로 admissions·공연 결과는 달라지지 않는다(1일 뒤 해시 일치 확인). 낮 구간에 `capacity` 를 읽는 코드가 생기면(예: SE-039/040 의 HUD 가 audience 의 capacity 를 읽는다면) 값이 다를 수 있다.
- 계약: SE-036 AC6 문구와 SN5("같은 seed → 같은 1일차 상태 해시")를 지키려고 `_new_world` 가 이중 restore 를 쓴다(기술 부채). 불러오기 경로에는 이 우회가 없다.
- 리플레이/세이브 비교 테스트가 "새 게임 직후 저장" 을 쓰면 가짜 불일치가 난다.

## 수정 방향 (2안)

**안 1 — 새 세계가 생성 직후 coverage 를 한 번 내보낸다 (발행 쪽을 고친다).**
`GameSession.new_game*` 끝(구독 등록 뒤)에서 `BuildSystem` 이 `build.coverage_changed {cause:"sync"}` 1회를 발행하게 한다(예: `BuildSystem.publish_sync()` 공개 함수, 또는 `new_game` 이 `time.phase_changed` 없이 직접 호출). 그러면 `AudienceSystem.coverage` 가 처음부터 `capacity 119` 이고 저장·로드가 일치한다. `_new_world` 의 이중 restore 우회도 지울 수 있다.
- 필요: events.md `build.coverage_changed` 발행 시점에 "새 세계 생성 직후(cause `sync`)" 추가, build.md #커버리지 "발행" 문구, 새 게임 직후 이벤트 순서를 확인하는 기존 테스트(`test_evening_entry_event_order` 등)와 `SE-036` 재발행 표 영향 점검.
- 위험: 새 게임 첫 이벤트가 하나 늘어 이벤트 열을 비교하는 테스트 기대값이 바뀐다.

**안 2 — 수신 쪽 초기값을 맞춘다 (`AudienceSystem` 이 빈 값으로 시작하지 않는다).**
`AudienceSystem._init` 이 `BuildSystem` 과 같은 빈 맵 coverage(`capacity 119` …)를 계산해 시작한다. 이벤트 수는 늘지 않지만 `AudienceSystem` 이 `BuildSystem` 의 계산(커버리지)을 복제하거나 `world/` 의 `Coverage` 를 직접 불러야 한다. "시스템끼리 직접 호출하지 않는다" 원칙(이벤트 버스)을 어기지 않으려면 `Coverage.empty_map()` 같은 `world/` 의 순수 함수를 두 시스템이 공유하는 형태여야 한다.
- 필요: `audience.md` 의 `coverage` 초기값 서술, `world/coverage.gd` 공개 함수, 감사 테스트.
- 위험: `AudienceSystem` 의 `_empty_coverage` 를 쓰는 새 게임 단위 테스트 기대값(capacity 0)이 바뀐다.

추천: 안 1(발행 한 군데, 의미가 "시스템이 서로 같은 coverage 로 시작한다" 로 분명). 어느 쪽이든 수용 기준은 아래와 같다.
