## 목표

시스템 7개(build·artist·audience·show·economy·reputation + TickLoop)를 `system_order` 순서로 만들고 등록하는 단일 조립점 `GameSession`(RefCounted)과, 그 스냅샷을 파일로 쓰고 읽는 `SaveFile`(core)을 만든다. 마감(close 진입)마다 오토세이브. 티어 1 루프 30일이 헤드리스에서 돌아가고(기준 배치 + 매일 섭외), 중간 저장·로드 뒤 진행이 연속 진행과 동일함을 리플레이 테스트로 고정한다. 이 티켓이 끝나면 "루프가 돈다" 가 헤드리스로 입증된다.

- 포함:

### 동작 요약

- **조립.** `TickLoop` 먼저(시간 명령 구독), 이어 `sim.json system_order` 를 돌며 build → artist → audience → show → economy → reputation 순으로 생성(= 구독 순서), 같은 순서로 4인자 `register_system(id, update, snapshot, restore)`. audience 는 `loop.rng`·`build_config.map` 을 받는다. 설정 하나라도 null 이거나 등록 실패면 `push_error` 1회, `false`, 세션 없음. 마지막에 GameSession 이 `session.save_requested`·`session.load_requested`·`time.phase_changed` 를 구독(시스템 뒤).
- **경계 처리.** `session.*` 명령은 명령 큐 → 경계 처리에서 핸들러가 요청만 기록. `advance`/`step` 은 시작 시 큐에 `session.*` 명령이 있으면 먼저 `loop.advance(0)`(경계 처리)를 하고 그 경계에서 저장·로드를 처리한 뒤 원래 구동을 한다. 큐에 `session.*` 이 없으면 TickLoop 호출 열은 TickLoop 직접 구동과 같다(리플레이 불변).
- **오토세이브.** `time.phase_changed {to:"close"}` 핸들러는 플래그만 세우고, `advance`/`step` 반환 뒤(close 홀드 경계) `saves_dir/autosave_day<N>.sav` 를 쓰고 `session.saved {slot:"autosave_day<N>", day}` 발행 → `autosave_keep > 0` 이면 일차가 작은 것부터 초과분 삭제(tick.md #스냅샷 "오토세이브 시점" 그대로).
- **경계 밖 호출.** `save_to`·`load_from`·`advance`·`step`·`snapshot`·`restore` 를 틱 처리 중(GameSession 구동 중) 또는 버스 디스패치 중(핸들러 안)에 부르면 `[GameSession]` `push_error` 1회 + 실패 값.

### 로드 뒤 재발행 규칙 (AC6, SE-049)

로드 성공 직후 아래 순서로 한 번 낸다(같은 `load_from`/`load_requested` 처리 안, 경계). 재발행 뒤 상태 해시는 파일 스냅샷 해시와 같다(테스트로 고정) — 구독 시스템은 같은 값으로 덮어쓸 뿐이다.

| # | 시스템 | 로드 뒤 이벤트 | 비고 |
|---|---|---|---|
| 1 | time(TickLoop)·show | `session.loaded {day, phase, speed, show_active}` | `show_active` = 그날 `show.started` 뒤 `show.ended` 전(`ShowSystem.status == "running"`). `time.phase_changed`·`time.speed_changed`·`show.started` 는 재발행하지 않는다(economy 정산·build sync·artist 라인업·reputation `show_day` 가 다시 반응, SE-049) |
| 2 | build | `build.placed` × 설치 수 (인스턴스 순서, 원래 페이로드와 같음: `cells` 재계산, `cost` = `paid`) | sim 구독자 없음. view(SE-037/038) 가 가구·조명을 다시 만든다 |
| 3 | build | `build.coverage_changed {cause:"sync", …}` (현재 커버리지 전체) | audience·show 가 같은 값으로 덮어씀(상태 불변). `cause` 는 기존 enum 의 `sync` 를 재사용 — 전용 값(`load`)이 필요하면 game-designer |
| 4 | reputation | `reputation.changed {day: 현재 일, delta: 0, total, by_genre}` | artist·audience 의 `reputation_total` 은 같은 값(불변). **재발행이라 delta 0** — SE-039 마감 리포트는 `session.loaded` 직후의 이 이벤트를 "명성 Δ" 로 쓰지 않는다 |
| — | economy | 재발행 없음. `GameSession.cash()`·`ticket_price()`·`hud_state()` 접근자로 읽는다 | `economy.cash_changed` 를 다시 내면 `delta`·`reason` 의미가 깨진다. SE-039 HUD 는 `session.loaded` 를 받으면 `hud_state()` 를 읽는다 |
| — | artist | 재발행 없음(`roster()`·`entry()`·`check_book()` 접근자) | `artist.lineup_set` 재발행은 audience 입장 결정(난수 소비)을 다시 일으킨다 |
| — | audience | 재발행 없음 | 저녁·공연이면 다음 틱 `audience.agent_moved`(UP5, 매 틱)로 군중이 다시 그려진다. 저녁 일시정지 상태로 로드하면 재개 전까지 군중이 안 보인다 → 후속 후보(아래) |

### 남은 것 · 후속 후보

1. **data_root 부분 적용.** `new_game(seed, data_root)` 는 각 Config 의 주 테이블 경로만 바꾼다. Config 내부의 교차 테이블(`tiers.json`·`economy.json`·`genres.json`·`artist.json`)은 Config 상수 경로 고정이다 → 테스트 데이터 루트를 통째로 바꾸려면 각 Config 로더에 루트 인자가 필요(sim/world 변경, 후속 티켓).
2. **잘린 gzip 의 엔진 오류.** Godot `decompress_dynamic` 이 잘린 스트림에 엔진 오류("Decompression failed")를 따로 1회 낸다. SaveFile 의 `push_error` 는 1회 그대로이고 테스트는 `assert_engine_error_count(1)` 로 처리했다. 막으려면 길이·CRC 를 따로 두는 포맷이 필요(현재는 순수 gzip 유지).
3. **군중 즉시 복구.** 저녁 일시정지(배속 0) 로드 시 `audience.agent_moved` 가 재개 전까지 없다. 재발행하려면 audience 가 공개 페이로드 접근자(`_moved_payload` 공개)를 내야 한다(sim 변경, 후속 — render 요청이 있으면).
4. **`session.new_game_requested`**(SE-039 AC5) 는 이 티켓 범위 밖이라 구현하지 않았다. GameSession 은 `new_game` 을 한 번만 허용하므로 새 게임은 새 `GameSession` 으로 만든다(구동 노드 몫).
5. **세이브 경계 의미.** `session.save_requested` 와 같은 경계 처리 묶음에 든 다른 명령(예: 뒤이은 `build.place_requested`)은 저장 전에 적용된다(한 경계 처리 = 큐 전체). session 명령이 있을 때만 `advance(0)` 경계 처리가 한 번 더 생긴다.
6. 테스트 중 만든 `user://probe_saves*`(리포지토리 밖, 프로브 실행 산물)는 hook 이 리포지토리 밖 쓰기를 막아 지우지 못했다. 게임 상태와 무관.
