# SE-003 성능 스파이크: 인스턴싱 캐릭터 5,000 + 동적 라이트 32, 60fps 측정

| 담당 에이전트 | render-engineer |
| 마일스톤 | 프리프로덕션 |

| 스펙 | docs/PRD.md#기술-요구사항 ("인스턴싱 캐릭터 5,000 + 동적 라이트 32개에서 60fps"), docs/adr/0001-engine-godot-4.md, docs/style-guide.md (캐릭터 ≤ 800 tri, 셰도우는 저해상도) |

## 목표

ADR-0001 의 조건부 결정을 확인한다. Godot 4.6 forward_plus 에서, 매 프레임 움직이는 로우폴리 캐릭터 5,000개(GPU 인스턴싱)와
매 프레임 움직이는 동적 라이트 32개가 **모두 화면 안에 보이는 상태로** 1080p 평균 60fps 가 나오는지 재현 가능한 절차로 측정하고 표로 남긴다.
통과/실패 판정은 숫자로만 한다. 실패 시 Unity 재검토는 사람의 결정이며 producer 가 ADR 티켓을 만든다. 이 티켓은 결론을 내리지 않고 측정만 한다.

## 범위

- 포함:
  - `project/view/perf/spike_crowd.tscn` + `spike_crowd.gd` — `MultiMeshInstance3D` 캐릭터 프록시(캡슐+박스 조합, ≤ 800 tri) 5,000개를 100×100m 평면에 배치. 매 프레임 CPU 에서 전 인스턴스 트랜스폼 갱신(실제 게임에서 sim 위치를 보간해 쓰는 경로와 같은 비용). `OmniLight3D`/`SpotLight3D` 혼합 32개, 매 프레임 위치·색 변화. 바닥·카메라는 SE-002 의 것. 인스턴스 수·라이트 수·셰도우 라이트 수는 씬의 `@export` 변수.
  - `project/view/perf/perf_stats.gd` — 프레임 시간 배열 → 평균 fps, 1% low fps, 평균/최대 프레임 ms 계산(순수 함수, 헤드리스 테스트 가능).
  - `project/tests/view/perf/measure_spike.gd` — `godot --path project res://view/perf/spike_crowd.tscn -- --measure --config=B` 로 실행 시: VSync 끄기(`DisplayServer.window_set_vsync_mode`), 1920×1080 창, 10초 예열, 30초 측정, `user://perf/SE-003_<config>.json` 저장 + 콘솔 표 출력. 키: `config, instances, lights, shadow_lights, avg_fps, p1_low_fps, avg_frame_ms, max_frame_ms, draw_calls, primitives, resolution, vsync, renderer, gpu, cpu, godot_version, commit`.
  - `project/tests/view/perf/results/SE-003.md` — 아래 구성 A~D 의 결과 표 + 측정 PC 사양.
  - `project/tests/view/test_spike_scene.gd`, `project/tests/view/test_perf_stats.gd`.
- 제외(다른 티켓):
  - 실제 캐릭터 모델·스켈레톤 애니메이션(art-pipeline), 임포스터·군중 셰이더(티어 4+ 티켓).
  - 툰 셰이더 적용 상태의 비용 — SE-004 에서 이 씬을 재사용해 측정.
  - 최소 사양(Intel Iris Xe 30fps) 측정 — 해당 하드웨어가 있을 때 사람 실행. 없으면 "검증 불가"로 기록.
  - 통과/실패에 따른 ADR 작성 — producer.

### 사람 PC 실행 명령 (구성 A~D 각 1회)

저장소 루트에서, Godot 에디터를 닫고 실행한다. 각 실행은 약 40초 뒤 스스로 종료한다.

```bash
mkdir -p docs/reports/perf
for c in A B C D; do
  godot --path project res://view/perf/spike_crowd.tscn -- --measure --config=$c --out="$PWD/docs/reports/perf/SE-003-$c.json"
done
```

(PowerShell 버전은 `results/SE-003.md` 에 있다.)

- **결과 JSON 위치 제안: `docs/reports/perf/SE-003-<config>.json`** (위 `--out`). qa 는 이 4개 파일을 읽어 `project/tests/view/perf/results/SE-003.md` 표와 대조한다. 이 경로는 qa·사람 쓰기 범위라 render-engineer 는 파일을 만들지 않았다.
- `--out` 을 빼면 `user://perf/SE-003_<config>.json` (Linux `~/.local/share/godot/app_userdata/Stage Empire/perf/`, Windows `%APPDATA%\Godot\app_userdata\Stage Empire\perf\`).
- 콘솔에 표 한 행(`| B | 5000 | 32 | 8 | avg | 1%low | avg ms | max ms | draw calls | primitives |`)과 `관문(B 평균 ≥ 60 fps): 통과/실패/무효` 가 찍힌다.
- JSON 키: 티켓 필수 17개(`config, instances, lights, shadow_lights, avg_fps, p1_low_fps, avg_frame_ms, max_frame_ms, draw_calls, primitives, resolution, vsync, renderer, gpu, cpu, godot_version, commit`) + `gate{config, min_avg_fps, applies, pass, verdict}`, `run_valid`, `run_issues`, `bound_hint`, `avg_gpu_ms`, `avg_render_cpu_ms`, `avg_crowd_update_ms`, `avg_process_ms`, `objects`, `video_mem_mb`, `ram_gb`, `os`, `gpu_api`, `gpu_driver`, `cpu_cores`, `instance_mesh_tris`, `p1_low_frame_ms`, `sample_count`, `warmup_sec/frames`, `measure_sec`, `timestamp` 등.
- **조건 위반이면 숫자와 관계없이 무효**: 헤드리스, VSync 가 off 가 아님, 렌더러가 forward_plus 가 아님, 실제 창 크기 ≠ 1920×1080 이면 `run_valid=false` 이고 B 의 `gate.verdict = "무효"`. 이런 JSON 은 표에 넣지 말고 다시 잰다.
- 구경용(측정 없음): `godot --path project res://view/perf/spike_crowd.tscn -- --config=B`. Q/E 회전, 휠 줌, WASD 팬.
- 동작 확인용 단축 인자 `--warmup-sec= --warmup-frames= --measure-sec=` 가 있다. 관문 측정에는 쓰지 않는다(JSON 에 실제 값이 남는다).

### 티켓과 다르게 한 것 (리뷰 확인 요청)

1. **군중 영역이 100×100 m 가 아니라 한 변 약 50.5 m 정사각형**(카메라 요에 맞춘 방향). SE-002 최대 줌아웃은 직교 size 32 m(16:9 가로 56.9 m)라서 100×100 m 는 화면에 다 들어가지 않는다. 범위의 "100×100 m" 와 AC2(전 인스턴스 프러스텀 안, 컬링으로 숫자를 깎지 않음)가 충돌해 AC2 를 따랐다. 한 변 = min(가로 폭, (size − 캐릭터 높이×cos 피치)/sin 피치) × `crowd_fill_ratio`(0.9) − 2×배회 반지름. 밀도는 B 약 2명/m², D 약 4명/m². 바닥 GridView 는 이 영역을 덮는 73×73 타일로 다시 만든다.
2. **인스턴스·라이트·셰도우 수는 개별 `@export` 가 아니라 `spike_configs.tres` 의 구성 행**이다. 씬 `@export` 는 `settings`(SpikeConfigSet)와 `config_id` 다(메인 세션 지시: 수치는 리소스에). 우선순위: `config_id` > `--config=` > `default_config_id`(B).
3. **측정기는 `project/tests/view/perf/measure_spike.gd`** 에 두고 `spike_crowd.gd` 가 `--measure` 일 때 경로 문자열로 로드한다. view/ 에 파일 쓰기를 금지한 `test_view_boundary.gd` 때문이다. 내보내기 빌드에 tests/ 가 빠지면 측정 모드는 오류 후 종료 코드 3 으로 끝난다(스파이크라 허용 범위로 봄).
4. 캐릭터 프록시는 예산 상한 근처의 최악 비용으로 잡았다: 캡슐(16 분할 × 6 링, 672 tri) + 머리 박스 + 팔 박스 2개 = **708 tri**, 한 서피스.
5. 셰도우 아틀라스는 비교를 위해 A~D 모두 2048. Omni 셰도우는 Godot 기본값(큐브)이다.
6. 군중 갱신은 "10 Hz 틱마다 다음 위치 계산 + 매 프레임 prev/next 보간 후 전 인스턴스 버퍼 재작성"으로 실제 게임 경로를 흉내 낸다(`interpolation_tick_hz`). sim 과는 연결하지 않는다.

### 남은 질문 / 발견

1. **셰도우 패스 비용이 지배적일 가능성이 크다.** llvmpipe 에서 B 의 primitives 가 A 의 25배(88.5M vs 3.54M)다. MultiMesh 1개 = AABB 1개라서 셰도우를 켠 라이트의 면마다(Omni 큐브 6면 × 4 + Spot 4 = 28패스) 군중 전체 3.54M tri 를 다시 그린다. forward_plus 에서도 패스 구조는 같으므로 B 가 GPU 바운드로 실패하면 원인 후보 1순위다. 이 티켓은 측정만 하므로 고치지 않았다. 실패하면 producer 가 판단할 후속 후보: (a) 군중 MultiMesh 를 32×32 청크로 나눠 라이트별 컬링(PRD 청크 단위), (b) `ArrayMesh.shadow_mesh` 에 저폴리 셰도우 메시, (c) Omni 셰도우를 dual paraboloid(2패스)로, (d) 군중은 위치 라이트 그림자를 드리우지 않음(아트 디렉션 결정).
2. **GDScript 군중 갱신 CPU 비용**: 이 Xeon 에서 5,000명 2.8 ms, 10,000명 5.4 ms(16.7 ms 예산의 17% / 32%). 티어 6 앞줄 5,000 + 군중 50,000 에서는 C#·GPU 애니메이션(셰이더에서 보간) 검토가 필요할 수 있다. 사람 PC JSON 의 `avg_crowd_update_ms` 로 확인한다.
3. 측정 창은 **테두리 없는 1920×1080**(1080p 모니터에서 제목 표시줄 때문에 창이 줄어드는 것 방지). 모니터가 1080p 보다 작으면 `run_issues` 에 "해상도 불일치"가 남아 무효가 된다. 그런 PC 에서는 이 측정을 할 수 없다.
4. `bound_hint` 는 `avg_gpu_ms` 와 `avg_crowd_update_ms + avg_render_cpu_ms` 를 비교한 대략값이다. AC8 분석 단락은 사람·qa 가 JSON 수치로 쓴다. `avg_process_ms`(Performance.TIME_PROCESS)는 프레임 전체 시간에 가까워 이 비교에 쓰지 않는다.
5. 최소 사양(Intel Iris Xe 30fps)은 범위 밖이다. 결과 표에는 "검증 불가(해당 하드웨어 없음)"로 적었다.
