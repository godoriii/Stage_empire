## 목표

SE-036 코드와 SE-039 가 정한 `session.*` 계약이 6곳 다르다. producer 결정: **코드가 계약을 따른다**(계약 변경 없음). SE-040 이 UI 와 세션을 붙이기 전에 맞춘다.

## 결정 (producer, SE-036 reviewer 추천 채택)

- `session.save_failed` 는 쓰지 않는다. SN3 대로 저장 실패는 `push_error` 만(UI 는 `session.saved` 가 안 오면 아무것도 표시하지 않는다 — MVP 범위). 필요해지면 계약을 바꾸는 별도 티켓.
- 불러오기 실패 사유는 SN4 의 5종과 판정 순서 그대로.
- 새 게임 명령 `session.new_game_requested {seed}` 와 SN5(버스 구독 유지)를 이 티켓에서 구현한다 — SE-040 은 이 명령만 발행한다.

## 범위

- 포함(sim-engineer, `project/core/game_session.gd` + 테스트)
  - `load_failed.reason`: `invalid`/`missing`/`corrupt`/`version_mismatch`/`restore_failed`, SN4 순서. `bad_slot`·`not_found` 제거.
  - `session.save_failed` 발행 제거(SN3).
  - 슬롯 형식 SN1 `^[a-z0-9_]{1,24}$`(`is_valid_filename` 대신). 키가 없으면 `load_failed.slot` 은 `null`.
  - SN2: 불러오기·새 게임 성공 뒤 같은 경계에 남은 명령 폐기. 실패한 불러오기는 큐 불변.
  - SN5: `session.new_game_requested {seed}` 처리 — 같은 `GameSession`·같은 `EventBus` 로 세계를 새로 만들고(구독 유지), `session.loaded {day:1, phase:"day", …}` + AC6 재발행. 같은 seed → `new_game(seed)` 와 같은 1일차 상태 해시.
- 포함(qa): 계약 ↔ 코드 키·열거 대조 테스트(events.md 를 파싱해 reason 열거 비교), 변이.
- 제외: UI 변경(SE-040), 데이터 필드(SE-057).

**결정·해석(남김)**

1. **`save_version` 불일치 → `version_mismatch`.** SN4 ④ 문장은 `schema_version` 만 말하지만 SE-036 리뷰 발견 1·제안 티켓이 "save_version 불일치 또는 schema_version 불일치"를 version_mismatch 로 고정하라고 했고, 파일 버전도 버전 불일치라 ④ 로 묶었다. 판정 순서는 ③(형식·최상위 키 10개) 뒤다. game-designer 가 SN4 ④ 문장에 save_version 을 넣을지 확인 필요.
2. **③ "스냅샷 형식"** = `{header, snapshot}` 객체·헤더/스냅샷 스키마 버전 일치·스냅샷에 `TickLoop.SNAPSHOT_KEYS` 10개가 모두 있음. 그래서 `systems` 없는 v1 스냅샷은 버전이 틀려도 `corrupt` 다(③ 이 앞).
3. **SN5 구현 방식.** 시스템은 구독 해제 API 가 없어 세계를 새 객체로 바꾸면 옛 시스템이 버스에 남는다. 그래서 `new_game(seed)` 와 같은 설정으로 임시 세계를 만들고 그 1일차 스냅샷을 지금 `TickLoop` 에 `restore` 한다(같은 TickLoop·EventBus·시스템·구독). 재발행 뒤 같은 스냅샷을 한 번 더 restore 한다 — 아래 4 때문이다. 새 게임 명령 1회 비용 = 임시 세계 생성 + restore 2회.
4. **발견(기존 버그, SE-036 경로): 첫 `build.coverage_changed` 전 세계의 저장 → 불러오기 해시 불일치.** `AudienceSystem.coverage` 는 첫 coverage 이벤트 전까지 빈 값(capacity 0)인데 빈 맵의 `BuildSystem.coverage()` 는 capacity 119 다. 그래서 새 게임 직후(설치 전·첫 저녁 전) 저장한 파일을 불러오면 재발행 `sync` 가 관객 coverage 를 채워 "재발행 뒤 해시 == 저장 시점 해시"(SE-036 AC6)가 깨진다(헤드리스 스크립트로 확인: false). 새 게임 경로는 3 의 재적용으로 막았고, 불러오기 경로는 이 티켓 범위 밖이라 고치지 않았다. 저녁 진입 sync 가 같은 값을 다시 넣으므로 진행 결과에는 영향이 작다. 후속 티켓 제안: **SE-0xx 새 세계 관객 coverage 초기값(game-designer → sim-engineer)** — (a) `new_game` 이 생성 직후 `build.coverage_changed {cause:"sync"}` 1회 발행(events.md 발행 시점 추가 필요) 또는 (b) 재발행에서 `sync` 를 빼고 view 가 `GameSession` 접근자로 읽기. 수용 기준: 설치 0·저녁 전 저장 → 불러오기 해시 == 저장 해시.
5. `session.new_game_requested` 의 음수 seed 는 `new_game(seed)` 와 같이 `SeededRng` 이 push_error 1회 후 posmod 로 접는다(events.md 는 "음수 포함, 특별한 뜻 없음"). 같은 결과라 SN5 에는 맞지만, 음수 seed 를 오류 없이 받으려면 events.md 와 rng 규칙 중 하나를 맞춰야 한다(game-designer).
