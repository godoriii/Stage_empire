## 목표

`project/core/`에 게임 시간의 단일 출처가 생긴다. 고정 10 tick/초로만 시간이 가고, 하루가 낮→저녁→공연→마감 4구간을 돌며,
배속 0~3이 구간별 허용 범위 안에서만 바뀌고, 모든 난수가 시드 고정 RNG 한 곳에서 나오며, 시스템끼리는 이벤트 버스로만 말한다.
"같은 시드 + 같은 명령 열 = 같은 상태"가 헤드리스 리플레이 테스트로 증명되면 끝이다. 화면은 없다.

- 포함:

  - `project/tests/sim/test_sim_config.gd`, `test_event_bus.gd`, `test_rng.gd`, `test_tick.gd`, `test_core_boundary.gd`, `replay/test_replay_tick.gd`.

### 구현 결정 (스펙 해석)

1. **명령 페이로드 숫자는 `int` 만 허용 (E4 보강, v0).** SE-006 리뷰 발견 1 의 (a) 안을 따랐다. `EventBus.publish()` 는 `*_requested` 페이로드 안(재귀)에 `float` 가 하나라도 있으면 정수값(`2.0`)이어도 `push_error` + `false`, 큐잉하지 않는다. 상태 이벤트는 기존 E4 대로 `float` 허용. 그 결과 `restore()` 5단계의 정규화가 "pending_commands 안의 정수값 float → int(재귀), 정수 아닌 float 가 있으면 복원 실패" 로 손실 없이 정의된다(`EventBus.normalize_commands`). `test_snapshot_restore_equivalence` 에 대기 명령이 남은 상태의 왕복 해시 비교를 넣었다(리뷰 후속 AC).
   - 이 때문에 tick.md 의 두 문장과 어긋난다: (a) #배속 "배속 요청 처리" 1행과 events.md `time.speed_requested` 의 "정수값 `float` 허용", (b) `test_speed_rejected_keeps_state` 의 "`1.5` → `reason:"invalid"`". 구현에서 `1.5` 는 버스가 `publish()` 단계에서 거부(false + `push_error`)하므로 `time.speed_rejected` 가 나지 않는다. 테스트는 이 동작(거부, 상태 해시 불변, 이벤트 0개)을 단언한다. `"fast"`·키 없음은 스펙대로 `reason:"invalid"`. `TickLoop` 의 배속 핸들러 자체는 스펙 표대로 정수값 float 를 정수로 인정하는 코드를 유지한다(버스를 거치지 않는 경로가 생겨도 표와 같게).
2. `restore()` 는 스펙의 검사(I1·I3·phase·day·schema_version)에 더해 **I4(`speed ∈ speeds`)와 `seed` 범위(0~2^31−1)** 도 검사한다(불변식 표가 "모든 경계 상태에서 참"이므로). 모든 검사 후에만 상태를 바꾼다(실패 시 불변).
3. `EventBus` 의 같은 핸들러 판정은 `Callable ==` 에 **바인드 인자 비교를 더했다.** Godot 의 `Callable ==` 는 `bind()` 인자를 구별하지 않아 `h.bind("a")` 와 `h.bind("b")` 를 같은 핸들러로 봤다(테스트로 확인).
4. `set_pending_commands(a)` 는 `bool` 을 돌려준다(형식 오류 시 `false`, 큐 불변). 스펙 API 표는 반환형을 정하지 않았다.
5. 구간 id `day, evening, show, close` 는 C1 검사용으로 `SimConfig.PHASE_IDS` 에 문자열로 있다(스펙이 이름·순서를 고정). 숫자 리터럴은 tick.md 상수표의 것(`1000000`, FNV 상수, `2147483647`)뿐이다.
