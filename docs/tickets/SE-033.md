## 목표

낮 구간의 `artist.book_requested` 를 받아 등급 가용·중복·구간을 검사하고 economy 에 개런티를 선지급 제안, 승인되면 오늘 라인업으로 확정한다. 저녁 진입에 `artist.lineup_set` 을 내고, `show.ended` 를 받아 성장·승급을 적용한다. 난수 없음(v0), Node 0.

## 범위

- 포함: `project/sim/artist_config.gd`(`ArtistConfig`: 두 테이블 로드·교차 검사 K — genre ∈ genres, grade ∈ guarantee_by_grade 키(economy K4 와 같은 방향), id 유일), `project/sim/artist_system.gd`(`ArtistSystem`: 상태·핸들러·성장·스냅샷 훅), 짝 테스트 2개. `TickLoop.register_system("artist", …)` 4인자. 명성 임계(rookie 가용)는 `reputation.changed` 구독으로 최신 `total` 을 캐시(reputation 시스템이 없을 때(SE-035 전) 기본 0 — local 만 가용).
- 제외(다른 티켓): 섭외 UI(SE-039), 관계·라이더·유출, 동적 개런티, 취소 명령.

### 구현 결정(결정 로그 후보, SE-032 선례를 따름)

1. **H2 `guarantee`** = `charge_resolved.amount`(정수가 아니면 제안 금액) — SE-032 결정 4 와 같다. 현재 economy 는 항상 제안 금액을 돌려준다.
2. **economy.json 직접 읽기** — `ArtistConfig` 가 `guarantee_by_grade` 를 Dictionary 로 읽고 `EconomyConfig` 를 만들지 않는다(SE-032 결정 5 의 `BuildConfig` 와 같은 방식, 깨진 economy 사본이 artist 로드를 무관한 이유로 막지 않게). `json_util.gd`(SE-044 C)가 main 에 없어 `ArtistConfig.as_int`·`read_json`·`_int_deep` 를 자체로 두었다(`as_int` 에 |f| ≥ 2^63 가드 포함 — SE-044 C 방향). SE-044 C 병합 뒤 통합 대상.
3. **입력 페이로드 검사** — `time.phase_changed` 는 `to ∈ SimConfig.PHASE_IDS` 이고 `day` 가 `int ≥ 1` 일 때만, `time.day_started` 는 `day` `int ≥ 1`, `reputation.changed` 는 `total` `int ≥ 0` 일 때만 반영. 아니면 `push_warning` + 무시(economy·build 선례의 경고 수준). RA2 의 "`phase ∈ sim.json phases[].id`" 도 `SimConfig.PHASE_IDS`(SimConfig C1 이 sim.json 과 같음을 보장)로 판정해 artist 가 sim.json 을 따로 읽지 않는다.
4. **스펙에 없는 오류 반환** — `unlock_reputation(모르는 등급)` = push_error + `-1`(`guarantee` 규약과 같게), `grow(모르는 등급|공연 등급)` = push_error + `{}`. 시스템 경로에서는 G5·RA4 가 먼저 막아 도달하지 않는다.
5. **로더 추가 검사(L 번호 밖)** — `guarantee_mode == "by_grade"`, `booking_phases ⊂ PHASE_IDS`, 명단 id 유일, 행·등급 필드 타입. 스키마와 같은 내용이며 사본 테스트·부분집합 검증기 대비.
6. **공개 API 추가(읽기 전용)** — `ArtistSystem.has_pending()`(AR8 단언용), `ArtistConfig.grade_ids()`·`genre_of(id)`. 상태를 바꾸지 않는다.

### 남은 질문

1. **`show.ended`·`reputation.changed` 는 아직 events.md 표에 없다**(SE-030 이 등록). 구현은 artist.md 의 `show.ended {day, artist_id, grade(영문 id)}`·`reputation.changed {total: int}` 를 가정했다. SE-030 스펙이 키 이름·타입을 다르게 정하면 G1·명성 핸들러를 맞춰야 한다.
2. **SE-036(`GameSession`) 인계** — 시스템 생성 순서를 `system_order`(build → artist → … → economy)로 해야 저녁 진입 꼬리가 `build.coverage_changed {sync}` → `artist.lineup_set` 순이 된다(artist.md #라인업 "전달 순서"). 이 티켓 테스트는 build 없이 artist → economy 순만 확인했다.
3. SE-034(audience)는 저녁 진입 계산을 `artist.lineup_set` 수신 시 해야 한다(artist.md 계약) — 이 구현은 `time.phase_changed {to:"evening"}` 핸들러 안에서 발행하므로 FIFO 상 모든 `time.phase_changed` 구독자 뒤에 전달된다.
