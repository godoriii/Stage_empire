## 목표

sim-engineer 가 SE-001 의 테스트를 질문 없이 쓸 수 있을 만큼 틱 루프의 보장 사항이 문서로 고정된다: 10 tick/초 고정,
하루 = 낮/저녁/공연/마감 4구간 전환, 배속 0~3 과 구간별 허용, "같은 시드 + 같은 명령 열 = 같은 상태"의 결정성,
세이브는 틱 경계에서만, 이벤트 버스의 발행·전달 순서. 이벤트 이름·페이로드는 `docs/gdd/events.md`에 확정된다.
이미 PRD·sim.json 에 결정된 값(10 tick/s, 구간 길이, 허용 배속)은 바꾸지 않고 의미를 고정한다. 바꿔야 하면 ADR 제안으로 producer 에게.

## 수용 기준

- [ ] AC1. **10 tick/초 고정.** 문서가 `sim.json.ticks_per_second`를 단일 출처로 지정하고, 1 게임일 = Σ `phases[].ticks` = 3,300틱 = 330초(1배속)임을 명시하며, 틱 수 변경은 ADR 필요라고 적는다. 코드에 틱·구간 리터럴을 두지 않는 규칙 명시. → producer 체크리스트
- [ ] AC2. **세션 4구간 전환.** 표로: 구간 id, 진입 조건, 이탈 조건, 길이 출처. `day→evening→show→close`는 누적 틱 경계, `close`(ticks 0)는 시간이 흐르지 않고 `time.next_day_requested` 명령으로만 다음 날 `day`로 간다. `tick`(전역, 세이브 간 누적), `day`(1부터), `tick_in_day`, `tick_in_phase` 네 카운터 정의와 전환 순간의 값(예: tick_in_day 1800 이 evening 의 0 인지 day 의 마지막인지) 확정. → producer 체크리스트, SE-001 AC3·AC4 의 테스트로 검증 가능해야 함
- [ ] AC3. **배속 0~3.** 의미(0 = 일시정지, k = 실시간 1초당 10k 틱), 구간별 허용은 `sim.json.phases[].speeds`, 허용 밖 요청은 거부(상태 불변 + `time.speed_rejected`), 구간 진입 시 현재 배속이 허용 밖이면 클램프 규칙(표: evening 진입 2·3→1, show 진입 0·2·3→1, close 진입 →0, 다음 날 day 진입 시 기본 배속)을 확정. 일시정지 중에도 명령 이벤트는 받아 큐에 쌓인다(PRD 접근성 "일시정지 중 모든 조작 가능"). → producer 체크리스트, SE-001 AC5·AC6
- [ ] AC4. **결정성.** "같은 시드 + 같은 순서의 명령 열 → 같은 상태·같은 이벤트 열" 규칙. 명령 이벤트는 받은 즉시가 아니라 다음 틱 경계에서 처리(큐). 한 틱 안의 순서: 명령 처리 → 시스템 업데이트(고정 등록 순서, v0 목록) → `tick.advanced`. 실시간 입력(`step(delta)`)은 틱 수로만 환산되고 상태에 delta 가 직접 들어가지 않는다. RNG: `core/rng.gd` 만 허용, v0 스트림 목록(예: `audience`, `artist`, `events`, `economy`, `world`)과 파생 시드 규칙(마스터 시드 + 스트림 이름 → 스트림을 추가해도 기존 스트림 열이 바뀌지 않음). 리플레이 테스트의 "상태 해시" 정의(`snapshot()` JSON 문자열). → producer 체크리스트, SE-001 AC7·AC9·AC11
- [ ] AC5. **세이브는 틱 경계.** 스냅샷 필드 목록 `schema_version, seed, tick, day, phase, tick_in_phase, speed, rng{stream: state}` + 모두 기본형. 틱 처리 중(핸들러 안) 스냅샷 금지와 그때의 동작(빈 Dictionary + 오류). 복원 후 진행 = 연속 진행. 오토세이브 시점 = `close` 진입 틱(PRD "하루 마감마다"). → producer 체크리스트, SE-001 AC10
- [ ] AC6. **이벤트 버스 발행 순서.** 구독 순서대로 전달, 디스패치 중 발행은 FIFO 큐잉(재진입 없음), 페이로드는 기본형·배열·Dictionary 만, 명령 이벤트(`*_requested`)는 틱 경계 적용, 상태 이벤트는 그 틱 안에서 발생 순서대로, `tick.advanced`가 그 틱의 마지막 이벤트. → producer 체크리스트, SE-001 AC7·AC8
- [ ] AC7. `docs/gdd/events.md` 갱신: `tick.advanced {tick, phase}`, `time.speed_requested {speed}` 확정 + `time.phase_changed {from, to, day, tick}`, `time.speed_changed {speed}`, `time.speed_rejected {speed, reason}`, `time.next_day_requested {}` (필요 시 `time.day_started {day}`) 추가. tick.md 에 등장하는 이벤트 이름이 전부 표에 있다(0개 누락). → reviewer 대조
- [ ] AC8. 수용 기준 절이 SE-001 의 테스트 케이스 목록과 1:1 이다: `docs/tickets/SE-001.md`의 AC1~AC12 각각에 대응하는 `project/tests/sim/<파일>::<케이스>` 항목이 있고, 문서가 이름을 바꿨다면 SE-001 의 이름 대신 쓸 이름을 명시한다. → producer 대조
- [ ] AC9. `sim.json`/스키마를 바꿨으면 `version` 2 + `python3 tools/validate_data.py --strict` 통과 + 변경 이력. 안 바꿨으면 "변경 없음" 한 줄. → qa 실행 로그
- [ ] AC10. 열린 질문 절에 사람 결정 항목이 선택지 + 추천으로 있다(최소: 저녁 구간 2배속 허용 여부(현재 `[0,1]`), 공연 중 일시정지 불가 유지 여부(현재 `pausable: false`), close 에서 자동 다음 날 vs 명령 대기). → producer 가 `docs/status/`로 옮긴다
- [ ] AC11. `docs/gdd/README.md`의 tick.md 상태가 "v0"다. → producer 확인

**바뀐 테이블: `sim.json` v2.** 기존 값(10 tick/s, 1,800/600/900/0, 허용 배속, pausable)은 그대로다. 추가된 필드는 아래와 같다.
- `max_ticks_per_step: 30`: `step()` 한 번에 처리할 최대 틱 수. 프레임이 끊긴 뒤 밀린 틱을 몰아서 처리하지 않게 막는다.
- `snapshot_schema_version: 1`
- `rng_streams: [audience, artist, events, economy, world]`
- `system_order: [build, staff, artist, audience, show, crisis, economy, reputation]`
- `phases[].default_speed`: 1 / 1 / 1 / 0
- `phases[].enter_speed_mode`: force / keep_if_allowed / keep_if_allowed / force. 이 값과 `default_speed`로 클램프 표가 그대로 나온다: evening 진입 2·3→1, show 진입 →1, close 진입 →0, 다음 날 →1.

스키마 변경: 새 필드 필수화, `version` `enum [2]`, `phases` `maxItems 4`, `speeds` `minItems 1`·`uniqueItems`. 변경 이력은 tick.md#변경-이력에 있다.

**validate 결과.** `python3 tools/validate_data.py --strict` → `3개 테이블 스키마 검증, 실패 0` (exit 0). 음성 검사도 했다. version 1, 잘못된 mode, 스트림 중복, 구간 5개, default_speed 누락, tps 20 각각 1건씩 거부된다(jsonschema 4.26).

**SE-001에 영향을 주는 결정** (SE-001 AC 문구는 내 쓰기 범위 밖이라 producer가 반영해야 한다)
1. 스냅샷에 `pending_commands`를 추가했다. SE-001 AC10의 괄호 목록 대신 tick.md#스냅샷 표(9개 키)를 쓴다. 이유: 마지막 틱의 핸들러나 UI가 보낸 명령이 세이브에서 사라지면 복원 후 진행이 연속 진행과 달라진다.
2. 명령 큐는 `EventBus`에 둔다. `*_requested`는 publish 시 큐에 쌓이고 `dispatch_commands()`로 전달된다. 그래서 EventBus API가 SE-001 범위의 `subscribe/unsubscribe/publish`보다 늘어난다: `dispatch_commands`, `is_dispatching`, `get/set_pending_commands`.
3. `advance(n)`도 일시정지(speed 0)와 close에서는 멈춘다. `advance(0)`은 명령만 적용한다.
4. RNG 상태는 10진 문자열로 직렬화한다(int64가 JSON 왕복에서 손실되므로). 마스터 시드는 0~2^31−1이다. 파생 시드는 `"<seed>:<name>"`의 FNV-1a 32이며 검증 벡터 8개가 tick.md에 있다.
5. `TickLoop.register_system(id, Callable)`을 추가했다. 시스템은 `system_order` 순서로 호출된다.
6. "SE-006 추가" 테스트 케이스 8개를 SE-001 AC 아래에 붙였다: AC1 1, AC4 1, AC6 1, AC7 2, AC8 1, AC9 1, AC10 1. SE-001의 기존 케이스 이름은 바꾸지 않았다.
