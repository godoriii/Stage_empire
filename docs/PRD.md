# Stage Empire: 라이브클럽에서 글로벌 페스티벌까지 — PRD & 제작 계획

작성일 2026-10-09 · 작성자 현구

## 개요

**Stage Empire**(가제)는 지하 라이브클럽 사장으로 시작해 초대형 글로벌 음악 페스티벌 주최자가 되는 2D 아이소메트릭 건설·경영 시뮬레이션이다. 플레이어는 공간을 짓고, 아티스트를 섭외하고, 공연을 열어 번 돈과 명성으로 더 큰 무대로 올라간다.

| 항목 | 내용 |
|---|---|
| 장르 | 건설·경영 시뮬레이션(타이쿤) + 라이트 전략 |
| 시점 | 2.5D 아이소메트릭: 3D 로우폴리 모델 + 직교 카메라 + 툰 셰이더, 타일 기반 건설 |
| 플랫폼 | PC(Steam) 1순위, 이후 Nintendo Switch·모바일 검토 |
| 플레이 시간 | 1회차 20~30시간, 샌드박스 무제한 |
| 핵심 판타지 | "내 손으로 키운 씬(scene)": 무명 밴드를 발굴해 내 무대에서 스타로 만든다 |
| 레퍼런스 | Two Point Hospital(경영 톤·2.5D 룩), Prison Architect(배치 깊이), Game Dev Tycoon(성장 서사), Festival Tycoon(소재) |
| 타깃 유저 | 25~40세 타이쿤·시뮬레이션 팬, 음악 페스티벌 경험이 있는 인디 음악 애호가 |
| 비즈니스 모델 | 유료 패키지(약 20달러), 출시 후 장르·지역 DLC |

기존 타이쿤과 다른 점은 셋이다. 하나, 공간 규모가 **실내 클럽에서 야외 수만 명 부지까지 6단계로 바뀌며** 건설 규칙 자체가 달라진다. 둘, 아티스트가 소모품이 아니라 **함께 성장하는 캐릭터**로, 내 무대에서 커리어를 쌓은 아티스트가 헤드라이너로 돌아온다. 셋, 공연은 정적인 수익 계산이 아니라 **라인업·동선·음향·날씨가 맞물리는 실시간 이벤트**다.

## 목표와 성공 지표

출시 1년 내 Steam 판매 10만 장, 리뷰 긍정 비율 85% 이상을 목표로 한다. 그 전에 버티컬 슬라이스로 "클럽 한 곳을 키우는 2시간이 재미있는가"를 먼저 검증한다.

**제품 목표**

1. 건설과 경영이 서로 영향을 주는 상호작용 루프를 10분 안에 체감시킨다.
2. 6단계 성장이 각각 "새 게임처럼" 느껴지되 기존 지식이 유효해야 한다.
3. 아티스트와의 관계가 플레이어에게 이야기로 남는다.
4. 아이소메트릭 화면이 그 자체로 스크린샷을 찍고 싶은 정도로 매력적이어야 한다.

**비목표(Non-goals)**

- 멀티플레이·온라인 기능(리더보드 정도만 검토)
- 실제 아티스트 라이선스 음원 사용
- 사실적 3D 그래픽과 자유 카메라 회전(툰 셰이더 룩 고정, 90도 단위 회전만)
- 리듬 게임식 공연 미니게임

**KPI**

| 지표 | 목표 | 측정 시점 |
|---|---|---|
| 버티컬 슬라이스 테스트 재플레이 의향 | 70% 이상 | 버티컬 슬라이스 완성 시 |
| 튜토리얼 완주율 | 80% 이상 | 얼리 액세스 |
| 티어 3(도심 베뉴) 도달률 | 50% 이상 | 얼리 액세스 |
| 평균 플레이 시간 | 15시간 이상 | 출시 후 3개월 |
| Steam 리뷰 긍정 비율 | 85% 이상 | 출시 후 1개월 |
| 처리 성능 | 티어 6 관객 5,000명 표시 시 60fps | 알파 마일스톤 |

## 핵심 게임플레이 루프

한 사이클은 "공간을 짓고, 아티스트를 섭외하고, 공연을 치르고, 번 돈과 명성으로 더 크게 짓는다"이다. 공연 하나가 게임 내 하루의 클라이맥스이며, 그 결과가 다음 사이클의 자원과 선택지를 바꾼다.

*[그림: 핵심 게임플레이 루프 · 5단계 순환]*

공연 운영이 루프의 심장이다. 관객 만족도는 라인업 궁합, 음향 커버리지, 동선 혼잡, 바 대기열, 화장실 수, 날씨가 함께 결정하며, 이 값이 수익과 명성으로 환산되어 다음 티어의 문을 연다.

**세션 구조(게임 내 시간)**

| 구간 | 플레이어가 하는 일 | 게임 속도 |
|---|---|---|
| 낮(준비) | 건설·배치, 섭외, 스태프 배정, 가격 책정, 홍보 | 일시정지 가능, 1~3배속 |
| 저녁(개장) | 입장 흐름 관찰, 긴급 대응(장비 고장, 혼잡, 민원) | 실시간, 일시정지 가능 |
| 공연 | 아티스트 무대, 관객 반응 실시간 표시, 돌발 이벤트 | 실시간 |
| 마감(정산) | 수익·만족도·명성 리포트, 아티스트 관계 변화, 해금 알림 | 리포트 화면 |

티어 1에서는 하루가 한 공연이지만, 티어 5~6에서는 하루가 3일짜리 페스티벌의 하루가 되어 여러 무대가 동시에 돌아간다. 같은 네 구간이 유지되므로 플레이어의 습관은 끝까지 유효하다.

**플레이어 판타지**

- 무명 밴드를 50명 앞에서 처음 세운 사람이 5년 뒤 5만 명 앞에 그 밴드를 헤드라이너로 올린다.
- 좁은 지하실의 배관과 콘센트 위치까지 고민하던 사람이 들판에 도시를 짓는다.
- 내가 고른 장르 색깔이 "이 페스티벌만의 정체성"으로 평판에 남는다.

## 성장 티어(진행 구조)

6개 티어는 각각 새 맵, 새 건설 규칙, 새 시스템 하나를 더한다. 티어 이동은 명성 임계치와 자금을 동시에 충족해야 가능하며, 이전 시설은 팔거나 위성 베뉴로 유지할 수 있다.

| 티어 | 공간 | 수용 규모 | 해금 조건 | 새로 들어오는 시스템 | 주요 압박 |
|---|---|---|---|---|---|
| 1 | 지하 라이브클럽 | 50~150명 | 시작 | 기본 건설, 로컬 밴드 섭외, 바 수익 | 소음 민원, 임대료, 화재 규정 |
| 2 | 지상 라이브하우스 | 300~600명 | 명성 500, 자금 3만 | 음향·조명 설비 등급, 스태프 고용, 정기 이벤트 | 경쟁 베뉴 등장, 장비 고장 |
| 3 | 도심 콘서트 베뉴 | 1,500~3,000명 | 명성 2,000, 자금 20만 | 좌석 배치, 굿즈 샵, 스폰서 계약, 아티스트 전속 | 교통·주차, 암표 업자 |
| 4 | 야외 원데이 페스티벌 | 5,000~10,000명 | 명성 6,000, 자금 100만 | 다중 무대, 날씨, 화장실·급수 인프라, 푸드 존 | 폭우, 안전 사고, 타임테이블 충돌 |
| 5 | 사흘짜리 캄핑 페스티벌 | 20,000~40,000명 | 명성 15,000, 자금 500만 | 캄핑 존, 밤새 운영, 드론·미디어 중계, 현지 지역사회 | 쓰레기·위생, 팬 기대치, 헤드라이너 취소 |
| 6 | 글로벌 메가 페스티벌 | 80,000명 이상 | 명성 40,000, 자금 3,000만 | 해외 지부(프랜차이즈), 글로벌 투어 유치, 레거시 엔딩 | 연도별 트렌드 변화, 정체성 희석 |

금액은 게임 내 화폐 기준이며 밸런스 시트에서 투닝한다. 티어 2까지는 약 2시간 안에 도달해야 하고, 티어 4가 게임의 중반 피크다. 티어 5와 6은 새 맵이 아니라 **같은 부지가 확장되는 구조**로, 플레이어가 지금까지 지은 것을 버리지 않게 한다.

## 핵심 시스템 상세

여덟 시스템이 서로 입력과 출력으로 물린다. 각 시스템은 데이터 테이블(JSON)로 정의해 코드 수정 없이 밸런스를 바꿀 수 있어야 한다.

| 시스템 | 핵심 규칙 | 입력 | 출력 |
|---|---|---|---|
| 건설·배치 | 타일 그리드 위 방·벽·가구·설비 배치. 무대는 음향 반경, 출구는 피난 용량, 바는 서비스 반경을 가진다 | 자금, 부지 크기, 해금 목록 | 수용 인원, 음향·시야 커버리지 맵, 유지비 |
| 아티스트 | 장르, 인기, 실력, 성격, 요구 사항(라이더), 내 베뉴와의 관계도. 공연마다 성장하고 타 베뉴에 빼앗길 수 있다 | 섭외 제안, 공연 결과 | 개런티 요구, 관객 흐인력, 관계 이벤트 |
| 공연 | 실시간 시뮬레이션. 만족도 = 라인업 궁합 × 음향 × 시야 × 편의 − 혼잡 − 대기 | 라인업, 공간 상태, 관객 구성 | 만족도, 수익, 사고 이벤트 |
| 관객 | 취향 분포를 가진 에이전트. 입장 → 이동 → 관람 → 소비 → 퇴장 상태 기계. 티어 4부터는 개별 에이전트 + 밀도 흑리스틱 혼합 | 라인업, 티켓 가격, 명성, 홍보 | 입장 수, 소비, 만족도, 혼잡 히트맵 |
| 경제 | 수익: 티켓·주류·음식·굿즈·스폰서·중계권. 비용: 개런티·임대·인건비·유지비·세금. 파산 시 게임 오버. 파산 전 긴급 대출·스폰서 구제 기회를 몇 회 부여(횟수는 밸런스 시트) | 모든 시스템 | 현금 흐름, 파산 조건 |
| 명성 | 장르별 명성 벡터 + 종합 명성. 티어 해금과 섭외 가능 아티스트 등급을 연다. 실패한 공연은 명성을 깎는다 | 만족도, 미디어 노출 | 섭외 풀, 스폰서 제안, 관객 기대치 |
| 스태프 | 보안·음향·바·청소·의료·운영. 숙련도와 피로도를 가진다. 담당 구역 배정 | 고용 예산, 구역 지정 | 대기열 해소 속도, 사고 대응 속도 |
| 이벤트·위기 | 날씨, 장비 고장, 노쇼, 민원, 사고, 바이럴 히트. 확률은 티어와 준비 상태에 따라 가중 | 티어, 시설 상태, 스태프 | 선택지 팝업, 만족도·수익 변동 |

**아티스트 성장 경로**: 로컬 → 신인 → 중견 → 헤드라이너 → 레전드. 내 베뉴에서 처음 섭외한 아티스트는 "발굴 보너스"로 개런티 할인과 우선 섭외권을 주며, 이 관계가 후반 티어에서 헤드라이너 확보의 핵심 전략이 된다.

**장르 매트릭스**: 록, 힙합, 일렉트로닉, 인디, 재즈, 팝, 메탈, 월드 8장르. 관객 취향과 아티스트 장르의 유사도가 만족도에 영향을 주고, 한 장르에 집중하면 정체성 보너스, 섮으면 관객 폭 보너스를 받는다.

## 아이소메트릭 렌더링과 UX 요구사항

3D 로우폴리 모델을 직교(orthographic) 카메라로 내려다보는 2.5D 방식이다. 화면은 2D 아이소메트릭처럼 읽히지만 깊이 정렬·조명·카메라 회전은 3D 엔진이 처리한다. 모든 오브젝트는 1m 단위 타일 그리드에 스냅되고, 카메라 각도는 고정(피치 약 30도, 요 45도)이다.

| 영역 | 요구사항 |
|---|---|
| 그리드 | 1타일 = 1m. 티어 1: 24×24, 티어 6: 400×400. 청크 단위(32×32) 로드와 컴링. 야외 티어는 높이맵 지형 |
| 카메라 | 직교 투영, 팬, 줌 4단계, 90도 단위 회전 4방향(추가 에셋 비용 없음). 실내 티어는 카메라 쪽 벽 컷어웃 |
| 렌더링 | 툰 셰이더 + 외곽선 패스로 2D 느낌 고정. 그림자는 저해상도 셰도우맵, 야외는 캐스케이드 1단계 |
| 배치 규칙 | 드래그로 방 영역 지정, 단일 타일 가구 클릭 배치. 레이캐스트로 타일 판정. 유효·무효 타일 색 표시, 설비 반경 오버레이 표시. 회전 R, 취소 Esc, 철거 환불 70% |
| 오버레이 모드 | 음향 커버리지, 시야, 혼잡도, 관객 만족도, 수익성 히트맵. 지형에 투영되는 데칼로 표시, 킭키 한 개로 전환 |
| 관객 표현 | 티어 1~3: 개별 로우폴리 캐릭터(GPU 인스턴싱). 티어 4~6: 앞줄 개별 + 뒷줄 임포스터(빌보드)·군중 셰이더 |
| 조명·분위기 | 동적 조명이 핵심 매력. 스포트라이트, 무빙 헤드, 레이저, 안개 볼륨, LED 월을 3D 라이트와 파티클로 구현. 무대 연출 등급이 조명 개수·종류로 드러난다 |
| UI 구성 | 하단: 건설 팔레트. 상단: 자금·명성·날짜·속도. 우측: 알림 피드. 전체화면 패널: 아티스트 섭외, 스태프, 재무, 리포트 |
| 조작 | 마우스+키보드 1순위, 게임패드 커서 모드 지원(Switch 대비). 모든 액션은 키 리맵 가능 |
| 접근성 | UI 배율 100~150%, 색약 팔레트, 일시정지 중 모든 조작 가능 |

아트 스타일은 **로우폴리 + 플랫 컴러 머티리얼 + 툰 셰이더·외곽선**이다. 모델 하나가 모든 각도·줌·조명 조건을 커버하므로 스프라이트 방식보다 에셋 변형 수가 1/4 이하로 줄고, AI 3D 생성 후 사람 리터치 파이프라인과 맞는다. 2D 스프라이트 방식을 버린 이유는 다중 타일 오브젝트의 깊이 정렬, 90도 회전마다 4배 에셋, 무대 조명 표현 한계 때문이다. 최종 룩은 프리프로덕션에서 셰이더 시안 3종을 비교해 확정한다.

## 기술 요구사항

엔진은 **Godot 4.x(GDScript + 일부 C#)** 로 진행한다(결정). 2.5D 전환으로 3D 성능이 전제 조건이 됐으므로, 프리프로덕션에서 "인스턴싱 캐릭터 5,000 + 동적 라이트 32개에서 60fps" 스파이크를 가장 먼저 돌리고, 실패할 때만 Unity(URP 3D)를 재검토한다. 씬 파일이 텍스트라 에이전트가 읽고 쓰기 쉽고 로열티가 없다는 장점은 그대로다.

**렌더링 방식 비교(개발 용이성 기준)**

| 항목 | 2D 스프라이트 아이소 | 순수 3D(자유 카메라) | 2.5D(3D 모델 + 직교 카메라) |
|---|---|---|---|
| 초기 셋업 | 빠름, 타일맵·Y-sort 내장 | 느림 | 보통, 카메라·셰이더부터 잡아야 함 |
| 에셋 변형 | 회전 4방향 × 상태마다 스프라이트 | 모델 1개 | 모델 1개, 고정 각도라 LOD 단순 |
| 깊이 정렬 | 수동, 다중 타일 오브젝트가 고통 | 자동 | 자동 |
| 조명·무대 연출 | 2D 라이트 + 노멐맵으로 한계 | 자유 | 자유, 각도 고정이라 튜닝 쉬움 |
| 지형 높낮이 | 사실상 불가 | 가능 | 가능 |
| 군중 성능 | 가장 가벼움 | 인스턴싱·LOD 필수 | 인스턴싱 + 임포스터로 해결 |
| 룩 통제 | 그린 대로 나옴 | 툰 셰이더 필요, 각도마다 깨짐 | 툰 셰이더 1세트, 고정 각도라 안정 |
| 엔진 의존 | Godot 2D 매우 강함 | Godot 3D는 Unity보다 약함 | Godot 3D로 가능하나 성능 스파이크 필요 |
| 결론 | 소규모·MVP용 | 이 게임에는 과잉 | **채택** |

엔진 후보 비교는 아래와 같다.

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Godot 4.x | 무료, 텍스트 기반 씬, 가벼운 빌드, 로우폴리 3D에 충분, Switch 포팅 가능(파트너 경유) | 3D 대규모 인스턴싱·셰도우 성능은 Unity보다 약함, 콘솔 포팅 직접 불가 | **채택(결정). 성능 스파이크는 확인 절차** |
| Unity (URP 3D) | 에셋 스토어, 콘솔 포팅, 인력 풀, 검증된 3D 성능과 툰 셰이더 자료 | 바이너리 씬으로 에이전트 협업 불편, 라이선스 | 스파이크 실패 시에만 재검토 |
| 웹(Three.js/PixiJS) | 빠른 프로토타입, 브라우저 배포 | 대규모 시뮬레이션 성능, Steam 배포 복잡 | 프로토타입 전용 |

**아키텍처 원칙**

1. 시뮬레이션과 렌더링 분리: 게임 상태는 순수 데이터 모델, 렌더러는 이를 구독만 한다. 헤드리스 테스트와 배속의 전제다.
2. 고정 틱 시뮬레이션(10 tick/초), 렌더링은 보간. 세이브는 틱 경계에서만.
3. 데이터 주도: 가구·아티스트·장르·이벤트·티어 조건은 JSON 테이블. 스키마를 버전 관리하고 CI에서 검증한다.
4. 이벤트 버스로 시스템 간 결합 최소화. 시스템은 서로 직접 호출하지 않는다.
5. 관객 AI는 티어 3까지 개별 에이전트(최대 3,000), 그 이상은 흐름장(flow field) + 군중 밀도 모델로 전환한다.

| 레이어 | 책임 | 주요 모듈 |
|---|---|---|
| Core | 게임 루프, 틱, 세이브/로드, 이벤트 버스, RNG(시드 고정) | `core/` |
| Simulation | 경제, 관객, 아티스트, 공연, 명성, 이벤트 | `sim/` |
| World | 그리드, 배치 규칙, 경로 탐색, 커버리지 계산 | `world/` |
| Presentation | 직교 카메라, 모델·머티리얼 관리, 툰 셰이더, 조명·파티클, 군중 인스턴싱, 오디오 | `view/` |
| UI | 패널, HUD, 튜토리얼, 로컬라이즈 | `ui/` |
| Data | JSON 테이블, 스키마, 로컬 문자열 | `data/` |

**세이브**: 시뮬레이션 상태 전체를 직렬화(JSON → gzip), 스키마 버전과 마이그레이션 함수를 포함. 오토세이브는 게임 내 하루 마감마다.

**성능 목표**: 티어 6, 관객 5,000 개별 표시 + 군중 50,000 밀도 표현, 1080p 기준 60fps. 최소 사양은 내장 그래픽(Intel Iris Xe) 기준 30fps. 세이브 로드 3초 이내.

**테스트**: 시뮬레이션 레이어는 헤드리스 유닛 테스트 + 시드 고정 리플레이 테스트. 밸런스는 "봇 플레이어"가 1,000판 자동 플레이한 통계로 검증한다.

## 콘텐츠 범위

세 단계로 나눈다. MVP는 루프가 재미있는지만 확인하고, 버티컬 슬라이스는 최종 품질의 티어 1~2를 완성해 퍼블리셔·후원자에게 보여줄 수 있게 한다. 정식 출시는 6티어 전체다.

| 콘텐츠 | MVP | 버티컬 슬라이스 | 정식 출시 |
|---|---|---|---|
| 티어 | 1 (플레이스홀더 아트) | 1~2 (최종 아트) | 1~6 |
| 가구·설비 종류 | 20 | 80 | 350 |
| 아티스트 | 12 (텍스트만) | 40 (초상·성격) | 200 + 프로시저럴 생성 |
| 장르 | 3 | 5 | 8 |
| 관객 유형 | 3 | 6 | 12 |
| 스태프 직군 | 2 | 4 | 6 |
| 이벤트·위기 | 5 | 20 | 90 |
| 음악 트랙(장르별 공연 루프) | 3 | 10 | 48 |
| 효과음 | 15 | 60 | 250 |
| 튜토리얼 | 없음 | 티어 1 가이드 | 전체 + 시나리오 모드 3개 |
| 로컬라이즈 | 한국어 | 한국어, 영어 | 10개 언어 |
| 엔딩 | 없음 | 없음 | 레거시 엔딩 + 샌드박스 계속 |

아티스트 200명은 손으로 쓴 50명 + 템플릿 기반 생성 150명으로 채운다. 음악은 저작권 없는 오리지널 루프만 사용하며, 실제 아티스트·곡명은 패러디도 피한다.

## 에이전트 구성 계획

사람 한 명이 프로듀서 에이전트 하나만 상대하고, 프로듀서가 8개 전문 에이전트에 티켓을 배정한다. 전문 에이전트는 각자 담당 폴더만 수정하고, 검증 에이전트 둘을 통과한 PR만 병합된다. Claude Code의 `.claude/agents/*.md` 서브에이전트 + git worktree 병렬 작업을 전제로 한다.

*[그림: 에이전트 구성 · 오케스트레이터 1 + 전문 에이전트 8]*

설계·구현·에셋 세 레인은 서로 의존하지 않는 티켓에서 병렬로 돌고, 검증 레인은 모든 산출물이 거쳐야 하는 관문이다. 점선은 반려 경로로, 프로듀서가 새 티켓으로 되돌린다.

**에이전트별 역할과 경계**

| 에이전트 | 책임 | 쓰기 권한 | 산출물 | 권장 모델 |
|---|---|---|---|---|
| producer | 마일스톤 → 티켓 분해, 의존성 정리, 에이전트 배정, 병합, 사람에게 "플레이해볼 것" 보고 | 이슈, 병합 | 티켓 목록, 주간 상태 보고 | Fable 5.1 |
| game-designer | 시스템 규칙, 수치, 수용 기준, 밸런스 시트 | `docs/gdd/`, `data/` | 스펙 문서, JSON 테이블, 밸런스 리포트 | Opus 5.5 |
| content-writer | 아티스트 프로필, 이벤트 텍스트, 튜토리얼 문구, 로컬라이즈 | `data/text/`, `data/artists/` | 텍스트 JSON, 번역 파일 | Sonnet 5.5 |
| sim-engineer | 틱, 경제, 관객, 아티스트, 공연, 경로 탐색, 세이브 | `core/`, `sim/`, `world/`, `tests/sim/` | 코드 + 헤드리스 테스트 | Opus 5.5 |
| render-engineer | 직교 카메라, 툰 셰이더, 조명·파티클, 군중 인스턴싱, 배치 UI, HUD, 패널 | `view/`, `ui/`, `tests/view/` | 코드 + 스크린샷 비교 테스트 | Opus 5.5 |
| art-pipeline | 스타일 가이드 준수 모델 생성, 자동 검사, glTF 임포트, 메타데이터 | `assets/`, `data/furniture/` | 모델 + 검수 대기 목록 | Sonnet 5.5 + 3D 생성 도구 |
| audio | 장르 루프, 효과음, 버스·덤핑 설정 | `assets/audio/`, `data/audio/` | 오디오 파일 + 트리거 테이블 | Sonnet 5.5 + 오디오 생성 도구 |
| qa | 테스트 실행, 봇 플레이 1,000판, 성능 프로파일, 버그 재현 티켓 | `tests/`, 이슈 | 테스트 리포트, 밸런스 통계, 버그 티켓 | Sonnet 5.5 |
| reviewer | 아키텍처 경계(시뮬↔렌더 분리, 데이터 주도) 검사, 코드 리뷰 | 없음(읽기 전용) | 리뷰 코멘트, 승인/반려 | Fable 5.1 |

**책임 경계 규칙(CLAUDE.md에 명시)**

- 엔지니어 에이전트는 `data/`의 수치를 바꾸지 않는다. 밸런스는 game-designer만 손뎀다.
- render-engineer는 `sim/`을 읽기만 하고, sim-engineer는 `view/`를 건드리지 않는다. 경계를 넘어야 하면 티켓을 분리해 프로듀서에게 돌려보낸다.
- 생성 에셋은 사람 검수 없이 main에 들어가지 않는다. art-pipeline은 "검수 대기" 폴더까지만 책임진다.
- 모든 작업은 티켓 번호를 가진다. 티켓에는 수용 기준과 테스트 방법이 반드시 있다.
- 에이전트 간 전달은 대화가 아니라 파일로 한다: 티켓 → 스펙 파일 → PR 설명 → 리뷰 코멘트.
- 겁스 상태를 만드는 게임 스크립트는 헤드리스 테스트가 없으면 병합 불가. hooks로 강제한다.

**한 티켓의 흐름**

1. 사람이 마일스톤 목표를 producer에게 준다. 예: "티어 1 공연 루프가 돌아가게".
2. producer가 GDD를 참조해 티켓 10~20개로 쪼개고 의존성을 표시한다.
3. game-designer가 각 티켓의 스펙(규칙, 수치, 수용 기준)을 쓰고 JSON 초안을 넣는다.
4. sim-engineer와 render-engineer가 각자 worktree에서 병렬 구현하고 테스트를 함께 낸다.
5. art-pipeline과 audio가 같은 티켓의 에셋을 병렬로 만들어 검수 큐에 올린다.
6. qa가 헤드리스 테스트, 봇 플레이, 성능 측정을 돌리고 리포트를 낸다.
7. reviewer가 경계 위반과 코드 품질을 보고 승인하거나 반려한다. 반려는 새 티켓이 된다.
8. producer가 병합하고 빌드를 만들어 사람에게 "이번에 플레이해볼 것" 목록을 보고한다.

**리포지토리 구조**

```
stage-empire/
├─ CLAUDE.md                 # 아키텍처 원칙, 경계 규칙, 명령어, 티켓 형식
├─ .claude/
│  ├─ agents/               # producer, game-designer, content-writer, sim-engineer,
│  │                         # render-engineer, art-pipeline, audio, qa, reviewer
│  ├─ skills/               # 에셋 등록, 시트→JSON 내보내기, 헤드리스 테스트, 빌드
│  └─ settings.json         # hooks: 커밋 전 테스트·스키마 검증, 경계 위반 차단
├─ docs/
│  ├─ PRD.md                # 이 문서
│  ├─ gdd/                  # 시스템별 상세 설계
│  ├─ adr/                  # 아키텍처 결정 기록
│  └─ style-guide.md        # 아트 규칙, 팔레트, 폴리곤 예산, 타일 규격
├─ project/                 # Godot 프로젝트
│  ├─ core/  sim/  world/  view/  ui/  data/
│  └─ assets/ (models, materials, audio, review-queue/)
├─ tools/                   # 시트→JSON, glTF 임포터, 에셋 린터, 봇 플레이어
└─ tests/                   # sim/ view/ e2e/
```

**초기 세팅 순서**: CLAUDE.md와 아키텍처 골격 → reviewer와 qa 먼저 정의(검증이 없으면 병렬 작업이 무너진다) → sim-engineer로 틱·경제 스켈레톤 → render-engineer로 그리드 표시 → 나머지 에이전트 추가. 처음 2주는 에이전트를 3개 이하로 제한해 규칙이 작동하는지 확인한다.

## 마일스톤 로드맵

전체 76주(약 18개월)를 5단계로 나누고, 각 단계 끝에 통과 기준이 있는 관문을 둔다. 관문을 못 넘으면 다음 단계를 시작하지 않고 범위를 줄이거나 방향을 바꾼다. 1인 개발 + 에이전트 기준이며, 마당은 시간 순서만 나타내고 길이는 비례가 아니다.

*[그림: 마일스톤 로드맵 · 5단계, 76주]*

30주차 버티컬 슬라이스가 가장 큰 관문이다. 여기서 외부 테스터의 재플레이 의향이 70%에 미치지 못하면 프로덕션에 들어가지 않고 루프를 다시 설계한다. 퍼블리셔·후원 제안도 이 시점의 빌드로 한다. 1인 개발이므로 에이전트가 막히면 사람이 병목이 된다. 매주 사람 검수 시간을 먼저 확보하고 나머지를 에이전트 배정에 쓴다.

| 단계 | 주요 산출물 | 검증 방법 |
|---|---|---|
| 프리프로덕션 | CLAUDE.md, 아키텍처 골격, Godot 3D 성능 스파이크, 툰 셰이더 시안 3종, 에셋 파이프라인, 에이전트 9종 정의 | 스파이크 60fps 통과. 가구 1개가 요청부터 게임 화면까지 사람 개입 1회로 들어간다 |
| MVP | 티어 1 전체 루프, 관객 150명, 아티스트 12, 가구 20 | 내부 5명이 10분 플레이 후 "한 번 더"라고 말하는가 |
| 버티컬 슬라이스 | 티어 1~2 최종 품질, 튜토리얼, 음악 10트랙, 트레일러 | 외부 30명 테스트, 재플레이 의향 70%, 튜토리얼 완주 80% |
| 프로덕션 | 티어 3~6, 콘텐츠 전량, 봇 플레이 밸런스, 세이브 마이그레이션 | 봇 1,000판 파산율 10~25%, 티어 6 60fps, 크래시 0 |
| 폴리시·출시 | 베타 2회, 10개 언어, Steam 페이지·데모, 린어·Steam Deck 확인 | 베타 리뷰 긍정 85%, 위시리스트 목표 달성 |

## 리스크와 미결 사항

가장 큰 리스크는 "6단계 스케일 변화"가 게임 하나가 아니라 여섯 개의 반쪽짜리 게임이 되는 것이다. 버티컬 슬라이스에서 티어 1→2 전환이 연속적으로 느껴지는지를 최우선으로 확인해야 한다.

| 리스크 | 영향 | 완화책 |
|---|---|---|
| 티어마다 규칙이 달라 플레이어 지식이 단절 | 높음 | 건설·섭외·공연 UI를 전 티어 동일하게 유지, 새 시스템은 티어당 1개만 추가 |
| 에셋 350종 제작 분량 | 높음 | 생성 파이프라인을 프리프로덕션에서 확정, 모델 1개로 전 각도 커버, 머티리얼 색상 변형으로 종 수 확보 |
| 티어 5~6 군중 성능 | 높음 | 시뮬레이션·렌더 분리, 흐름장 전환, 인스턴싱·임포스터, 프리프로덕션에서 성능 스파이크 먼저 |
| 1인 개발의 검수 병목과 번아웃 | 높음 | 주당 에이전트 티켓 수 상한, 검수 시간 선확보, 사운드 외주, 버티컬 슬라이스 후 협업자 영입 검토 |
| Godot 3D 성능·툰 셰이더 룩이 기대에 못 미침 | 중간 | 프리프로덕션 4주 안에 스파이크 + 셰이더 시안 3종, 실패 시 Unity 전환을 그 시점에 결정 |
| 에이전트가 경계를 넘어 아키텍처 붕괴 | 중간 | reviewer 필수 통과, hooks로 폴더 쓰기 제한, ADR 기록 |
| 밸런스가 일찍 지루하거나 파산 빈발 | 중간 | 봇 플레이 통계를 매 마일스톤 검사, 시트 기반 수치 조정 |
| 음악 저작권·유사 아티스트 문제 | 중간 | 오리지널 루프만, 실존 아티스트 연상 이름 금지 철칙, 출시 전 법률 검토 |
| Festival Tycoon 등 유사작과의 차별화 부족 | 중간 | 아티스트 관계와 클럽→페스티벌 서사를 마케팅 전면에, 트레일러에서 성장 과정을 보여줌 |
